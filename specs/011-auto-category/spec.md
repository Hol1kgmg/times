# Feature Specification: 記事のカテゴリを AI で推定して振り分ける

**Feature Branch**: `011-auto-category`

**Created**: 2026-11-08

**Status**: Draft

**Input**: User description: issue #86「jev を使って自動カテゴリ割り振り機能」。jev の代わりにデプロイ先の Cloudflare Workers AI の clef を使う。AI が推定したカテゴリであることを画面で見て分かるようにする。分類に問題がなければそのまま DB に保存するので、推定かどうかは DB に持たない。登録するまでの間だけ示す状態とする。ローカル開発では推定を使わず、未分類のまま動かす (方針 A)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 貼り付けた記事がカテゴリの箱に自動で入る (Priority: P1)

管理者が登録・編集画面で記事の URL を貼り付けると、タイトルの取得に続いてシステムがカテゴリを推定し、候補を未分類ではなくそのカテゴリの箱に入れる。管理者は推定が正しければ何もせずに登録でき、間違っていればいつもどおりドラッグで別の箱へ移す。

**Why this priority**: 振り分けの手間を減らすことが、この機能の目的そのもの。

**Independent Test**: AI 系のニュース記事の URL を貼り付け、候補が未分類を経ずに「AI系」の箱に入ることを確認できる。

**Acceptance Scenarios**:

1. **Given** 登録画面, **When** 記事の URL を貼り付けて追加する, **Then** タイトルが入った後、候補は推定したカテゴリの箱の末尾に移る
2. **Given** 推定でカテゴリの箱に入った候補, **When** 何も直さずに登録する, **Then** そのカテゴリで保存される
3. **Given** 推定の結果を待っている候補, **When** 待つ間に管理者がその候補を手で別の箱へ移す, **Then** 推定の結果が届いても管理者が置いた箱から動かさない
4. **Given** 推定の確からしさが低い記事, **When** 推定が終わる, **Then** 候補は未分類に残る
5. **Given** 推定ができない (通信の失敗、ローカル開発で推定の手段がない), **When** URL を追加する, **Then** 候補は未分類に残り、エラーは出さず、これまでどおり手で振り分けられる
6. **Given** 編集画面, **When** URL を追加する, **Then** 登録画面と同じく推定したカテゴリの箱に入る

---

### User Story 2 - 推定で入った候補だと見て分かる (Priority: P1)

推定で箱に入った候補には、AI が推定したことを示す小さな印が付く。管理者は印を見て、確かめるべき候補を見分けられる。管理者が手で箱を移した候補は、管理者が決めたものなので印を外す。

**Why this priority**: 推定は間違うことがある。どれが確かめていない推定かが分からないと、誤った分類のまま登録してしまう。

**Independent Test**: URL を追加して推定で箱に入った候補に印が付き、その候補を別の箱へドラッグすると印が消えることを確認できる。

**Acceptance Scenarios**:

1. **Given** 推定でカテゴリの箱に入った候補, **When** 画面を見る, **Then** 候補に推定であることを示す印が付いている
2. **Given** 印の付いた候補, **When** 読み上げで候補を辿る, **Then** 推定のカテゴリであることが読み上げられる
3. **Given** 印の付いた候補, **When** 別の箱 (未分類を含む) へ移す, **Then** 印が外れる
4. **Given** 印の付いた候補, **When** 同じ箱の中で並び替える, **Then** 印は残る
5. **Given** 印の付いた候補を含む Digest, **When** 登録して編集画面で開き直す, **Then** どの候補にも印は付いていない

---

### Edge Cases

- 子記事にした候補: 親の箱に入るので、子記事としての印は持たない。親の候補の印は親の推定にだけ従う。
- 子記事から外した候補: 親と同じ箱に出るので、推定の印は付けない。
- タイトルが取れなかった候補: URL だけで推定し、確からしさが低ければ未分類に残す。
- 推定を待つ間に候補を消した: 推定の結果は捨てる。
- 推定を待つ間に箱の中で並び替えたり、タイトルを直したりした: 候補が未分類に残っていれば推定の箱へ移す。
- 推定の結果が届く順序が追加の順序と前後した: 各候補は自分の推定の箱の末尾に入る。並び順は届いた順になる。
- 推定を待つ間も追加の入力欄は使える状態を保つ (タイトルの取得を待つ間と同じ扱い)。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、登録・編集画面で追加された候補について、記事の URL とタイトルからカテゴリを固定 6 カテゴリのどれか 1 つに推定しなければならない (MUST)。
- **FR-002**: 推定の確からしさが一定の値に届かないときは、カテゴリを決めず、候補を未分類に残さなければならない (MUST)。
- **FR-003**: 推定したカテゴリは、候補がまだ未分類にあるときだけ適用し、その箱の末尾に移さなければならない (MUST)。管理者が既に移した候補は動かしてはならない (MUST NOT)。
- **FR-004**: 推定で箱に入った候補には、推定であることを示す印を付けなければならない (MUST)。印の意味は読み上げでも伝わらなければならない (MUST)。
- **FR-005**: 管理者が候補を別の箱へ移したら、その候補の印を外さなければならない (MUST)。
- **FR-006**: 推定かどうかは保存してはならない (MUST NOT)。保存する内容は、手で振り分けた場合と同じでなければならない (MUST)。
- **FR-007**: 推定に失敗したときは、候補を未分類に残し、管理者にエラーを示してはならない (MUST NOT)。手での振り分けは推定の有無に関わらず使えなければならない (MUST)。
- **FR-008**: 推定は管理者だけが使えなければならない (MUST)。任意の文字列で外部の推定を呼ばせないため。

### Key Entities

- **候補の推定の印**: 画面上の候補 1 件につき 1 つの真偽。推定で箱に入ったときに付き、管理者が箱を移すと外れる。保存しない。
- **カテゴリの推定**: URL とタイトルを入力に、固定 6 カテゴリのどれか、または「決められない」を返す。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 推定の手段がある環境では、追加した候補の過半数が未分類を経ずにカテゴリの箱に入る。
- **SC-002**: 推定で箱に入った候補は 100% に印が付き、手で移した候補に印が残る割合は 0% である。
- **SC-003**: 推定が失敗しても、候補の追加と登録ができる割合が 100% である。
- **SC-004**: 推定の有無によって保存される内容に差が出る件数が 0 件である。

## Assumptions

- 推定には、デプロイ先 (Cloudflare Workers) で使える Workers AI の clef を使う。jev は使わない。
- ローカル開発 (`just fe-dev`) には推定の手段がないので、推定をせず未分類のまま動かす。推定はデプロイ先でだけ働く。
- 確からしさのしきい値は最初 0.5 にし、運用しながら調整する。
- 推定はタイトルの取得が終わってから行う。タイトルがあるほうが推定が正確になるため。
- 推定の対象は追加したときの候補だけとする。既に箱にある候補を推定し直す操作は置かない。
- 印の見た目は `.agents/rules/frontend-ui-design.md` の「選べない理由」の型 (小さな `--color-brand` の印 + 読み上げ用のラベル) に寄せる。
