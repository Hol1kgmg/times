**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理者専用のページ・処理を管理者だけのものにする (Priority: P1)

読者や第三者が管理者専用のページの URL を開いても、そのページは存在しないものとして扱われ (404)、管理画面があること自体が分からない。管理者専用のサーバー処理も未ログインでは拒否される。ログイン画面は運用側だけが知る秘匿パスにあり、管理者はそこから GitHub でのログインを選び、GitHub 上で自分のアカウントとして承認するとトップページに移る。許可された GitHub ユーザー名以外で承認しても、ログインは成立しない。読者向けの一覧画面はログインの有無に関係なく今までどおり開ける。

本仕様では具体的な管理者専用ページは作らない。「管理者専用」と宣言したページ・サーバー処理を守る仕組みを用意し、後続の仕様 (記事登録画面 001 など) がそれを使う。

**Why this priority**: 管理者向けの機能は「公開環境に出す前に認証を先に導入する」と定めている。守る仕組みがなければ、後続の管理者向け機能を本番に出せない。この Story だけで公開の前提条件を満たす。

**Independent Test**: 管理者専用と宣言したページ・サーバー処理を未ログインで要求すると 404 または拒否になること、秘匿パスのログイン画面から許可された GitHub ユーザー名で承認するとトップページが開き管理者専用の処理が通ること、別の GitHub アカウントではログインが成立しないこと、同じブラウザで一覧画面がログインなしで開けることを確認できる。

**Acceptance Scenarios**:

1. **Given** ログインしていない状態, **When** 管理者専用と宣言したページの URL を開く, **Then** ページの内容は一切表示されず、存在しないページと同じ 404 の表示になる
2. **Given** ログインしていない状態, **When** 秘匿パスと異なる URL でログイン画面を開こうとする, **Then** 存在しないページと同じ 404 の表示になる
3. **Given** 秘匿パスのログイン画面が表示されている, **When** GitHub でのログインを選び、許可された GitHub ユーザー名で承認する, **Then** トップページが表示される
4. **Given** ログイン画面が表示されている, **When** 許可されていない GitHub アカウントで承認する, **Then** ログインは成立せず、このアカウントは管理者として許可されていない旨がログイン画面に表示される
5. **Given** GitHub の承認画面に進んだ, **When** 承認を取り消す (キャンセルする), **Then** ログインは成立せず、ログイン画面に戻る
6. **Given** ログインしていない状態, **When** 読者向けの一覧画面を開く, **Then** ログインを求められずに一覧が表示される
7. **Given** ログイン済みの状態, **When** 秘匿パスのページを開く, **Then** ログインを求められず、ログイン中であることとログアウトの操作が表示される
8. **Given** ログインしていない状態, **When** 管理者専用と宣言したサーバー処理を要求する, **Then** 処理は実行されず拒否される

---

### User Story 2 - ログイン状態を保ち、任意にログアウトする (Priority: P2)

管理者は一度ログインすれば、ブラウザを閉じて翌日開き直しても、再びログインせずに管理者専用の機能を使える。共用の端末で作業を終えたときなどは、秘匿パスのページからログアウトでき、以後は再びログインが必要になる。

**Why this priority**: 管理者の作業は日々のものなので、毎回のログインは手間になる。一方でログアウトの手段がなければ、端末を離れたときに保護の意味がなくなる。Story 1 で保護が成立していれば単体で運用は可能なため P2 とする。

**Independent Test**: ログイン後にブラウザを閉じて開き直し、秘匿パスのページがログイン中の表示になること、ログアウト操作の直後に管理者専用の処理を要求すると拒否されることを確認できる。

**Acceptance Scenarios**:

1. **Given** ログイン済みでブラウザを閉じた, **When** 有効期間内にブラウザを開き直して秘匿パスのページを開く, **Then** ログインを求められずにログイン中の表示になる
2. **Given** ログインしてから有効期間を過ぎた, **When** 管理者専用と宣言したページを開く, **Then** 存在しないページと同じ 404 の表示になる
3. **Given** ログイン済みで秘匿パスのページを開いている, **When** ログアウト操作をする, **Then** トップページに移り、直後に管理者専用の処理を要求すると拒否される
4. **Given** ログイン済みの状態, **When** 秘匿パスのページを見る, **Then** ログイン中であることとログアウトの操作が画面上で分かる
5. **Given** ログインしていない状態, **When** 読者向けの一覧画面を見る, **Then** ログイン・ログアウトに関する表示はない

---

### Edge Cases

- ログイン状態の有効期間中に、許可する GitHub ユーザー名が運用側で変更された場合、成立済みのログイン状態は影響を受けない。許可ユーザー名は新規ログインの入口の判定にだけ使い、ログイン後の本人識別は GitHub の固定 ID で行う。
- 管理者が GitHub 上でユーザー名を変更した場合、運用側で許可ユーザー名を更新するまで新規ログインは成立しないが、成立済みのログイン状態は固定 ID で識別されるため影響を受けない。旧ユーザー名を他人が取得しても、更新後は旧名でログインできない。
- 秘匿パスが運用側で変更された場合、旧パスは 404 になり、新パスでのみログイン画面が開く。成立済みのログイン状態は影響を受けない。
- 秘匿パスが読者向けの一覧画面などの既存の URL と重なる設定になっていた場合、既存の画面を優先し、ログイン画面は開けない。運用側が別のパスに設定し直す。
- GitHub に到達できない、または GitHub 側で承認が完了しなかった場合、ログインは成立せず、ログイン画面に戻って再試行できる。サービス内の他の画面には影響しない。
- 管理者専用のページを開いている最中に有効期間が切れた場合、次のサーバー処理の要求は拒否される。拒否の応答は、有効期間切れであることを画面が他のエラーと区別して判別できる形にする。既に開いている画面をどう扱うか (再ログインの案内など) はそのページの仕様に委ねる。
- ログアウト操作を 2 回連続で行っても、エラーにならずログアウト済みとして扱う。サービスからのログアウトは GitHub 側のログイン状態には影響しない。
- ブラウザがログイン状態の保存を許可していない場合、ログインは成立してもページを移ると 404 になる。サービス側はこれを検知せず、特別な表示はしない。
- GitHub からの戻り先 (callback) の URL は GitHub 側に固定で登録するため秘匿パスとは別に存在する。この URL を、ログイン画面から始めた正当なログインの流れ以外で開いた要求 (直接開く、流れの照合情報が欠ける・一致しない) は、存在しないページと同じ 404 として応答する。
- GitHub との連携情報、許可ユーザー名、秘匿パスのいずれかが運用側で未設定の状態では、ログイン画面も管理者専用のページも 404 になり、誰も開けない。無防備な状態で公開されることはない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは「管理者専用」と宣言したページとサーバー側の処理を、ログイン済みの管理者にだけ許可する仕組みを提供しなければならない (MUST)。未ログインの画面要求は、存在しないページと区別できない 404 として応答し、画面の内容もログイン画面への案内も返してはならない (MUST NOT)。未ログインのサーバー側処理の要求は拒否する (MUST)。本仕様では具体的な管理者専用ページは作らず、後続の仕様がこの仕組みを使う。
- **FR-002**: 読者向けの一覧画面 (002) と、それが使うサーバー側の処理は、ログインの有無に関係なく利用できなければならない (MUST)。本機能で一覧画面の表示を変えてはならない (MUST NOT)。
- **FR-003**: 管理者は 1 人だけとし、管理者として許可する GitHub ユーザー名は運用側が環境の設定として与える (MUST)。ログインが成立した管理者は backend に「管理者の記録」として固定 ID で保持する (MUST)。ユーザー登録、複数アカウント、権限の種類、許可ユーザー名の画面上での変更は本機能の範囲外とする。
- **FR-004**: ログインは GitHub アカウントによる本人確認で行い、サービス内にパスワードを持ってはならない (MUST NOT)。ログインが成立するのは、GitHub 上で承認したアカウントのユーザー名が許可ユーザー名と一致したときだけとする (MUST)。
- **FR-005**: 許可されていない GitHub アカウントで承認されたとき、または GitHub 側で承認が完了しなかったとき、システムはログインを成立させず、その旨をログイン画面上に表示しなければならない (MUST)。許可されなかったアカウントの情報をサービス内に保存してはならない (MUST NOT)。
- **FR-006**: ログイン画面は運用側が環境の設定として与える秘匿パスにだけ存在しなければならない (MUST)。それ以外の URL でログイン画面を開こうとした要求は 404 として応答する (MUST)。読者向けの画面にログイン画面への導線を置いてはならない (MUST NOT)。GitHub からの戻り先 (callback) の URL は、ログイン画面から始めた流れであることを照合できる要求にだけ応答し、それ以外の要求は 404 として応答しなければならない (MUST)。秘匿パス以外への要求に対して、ログイン画面の存在やログインの仕組みを示す表示を返してはならない (MUST NOT)。
- **FR-007**: ログイン状態はブラウザを閉じても保たれ、ログインから 30 日間有効でなければならない (MUST)。有効期間を過ぎたら未ログインとして扱う。
- **FR-008**: 管理者は秘匿パスのページから 1 回の操作でログアウトでき、直後から管理者専用のページは 404、管理者専用の処理は拒否になる (MUST)。ログアウト後はトップページを表示する。
- **FR-009**: ログイン済みの状態で秘匿パスのページを開いたときは、ログイン中であること (ユーザー名) とログアウトの操作が表示されなければならない (MUST)。未ログインの画面と読者向けの画面には表示しない (MUST NOT)。
- **FR-010**: ログイン済みの状態で秘匿パスのページを開いたときは、ログインの操作を出さず、FR-009 の表示にしなければならない (MUST)。
- **FR-011**: 許可ユーザー名の照合は GitHub 上のユーザー名と完全一致 (大文字小文字は区別しない) で行い、ログインの入口でだけ使わなければならない (MUST)。ログイン成立後の本人識別は、GitHub が各アカウントに割り当てる変更されない固定 ID で行わなければならない (MUST)。ログイン状態、および将来サービス内に管理者を表す記録を持つ場合、その識別子は固定 ID とし、ユーザー名を識別子にしてはならない (MUST NOT)。
- **FR-012**: GitHub との連携情報、許可ユーザー名、秘匿パスのいずれかが運用側で未設定のとき、システムはログイン画面を 404 とし、すべてのログインを失敗として扱わなければならない (MUST)。未設定を理由に管理者専用のページ・処理を開放してはならない (MUST NOT)。
- **FR-013**: 運用側が許可ユーザー名を変更しても、変更前に成立したログイン状態は影響を受けない (MUST)。変更は次回以降の新規ログインにだけ効く。秘匿パスの変更もログイン状態に影響しない。
- **FR-014**: 管理者専用のサーバー側処理を未ログイン・有効期間切れ・失効済みの状態で要求されたとき、拒否の応答は、ログイン状態が無効であることを画面が他のエラーと区別して判別できるものでなければならない (MUST)。判別した後の画面の振る舞い (再ログインの案内など) は、そのページの仕様が定める。秘匿パスは全画面に共通で配布される資材に含めてはならない (MUST NOT)。
- **FR-015**: GitHub との本人確認 (承認結果の検証)、ログイン状態の発行・照合・失効は backend が行わなければならない (MUST)。backend は管理者専用の処理への要求ごとにログイン状態を自分で照合し、frontend の判定結果を信用して省略してはならない (MUST NOT)。frontend はログイン画面の表示と、ログイン状態の識別子をブラウザと backend の間で運ぶことだけを担う。ブラウザが backend に直接到達する経路は引き続き設けず、backend への到達制限 (adr/backend/0006) は本機能で変更しない (MUST)。
- **FR-019**: ログイン状態は backend の記録として持ち、運用側は成立済みのログイン状態を個別に失効させられなければならない (MUST)。失効の画面は本機能の範囲外とし、運用側の操作 (記録の削除) で行う。
- **FR-016**: ログイン画面と、ログイン済みの秘匿パスのページに置くログアウトの操作は、既存の UI デザインルールとデザイン基礎資料 (Figma) の「ログインカード」「ログアウト」に従わなければならない (MUST)。
- **FR-017**: GitHub に求める権限は本人確認に必要な最小限 (公開プロフィールの参照) とし、リポジトリなど他の情報への権限を求めてはならない (MUST NOT)。
- **FR-018**: ログインに成功したとき、システムはトップページ (読者向けの一覧画面) を表示しなければならない (MUST)。ログイン前に開こうとしていた画面への復帰は行わない。トップページの表示はログイン後も変えない (FR-002)。

### Key Entities

- **許可ユーザー名**: 管理者として認める GitHub のユーザー名。運用側が環境の設定として 1 つだけ与え、画面からは変更しない。ログインの入口の判定にだけ使う。
- **固定 ID**: GitHub が各アカウントに割り当てる、ユーザー名を変えても変わらない識別子。ログイン成立後の本人識別と、サービス内で管理者を指すあらゆる記録の識別子として使う。
- **秘匿パス**: ログイン画面が置かれる URL のパス。運用側が環境の設定として与え、公開しない。読者向けの画面からは辿れない。
- **GitHub 連携情報**: サービスが GitHub に本人確認を依頼するために運用側が設定する情報。承認結果を検証する秘密情報は backend だけが持つ。サービス内にパスワードは存在しない。
- **管理者の記録**: ログインが成立した管理者を backend が保持する記録。固定 ID を識別子とし、表示用にユーザー名を添える。将来 Digest の登録者を指すときはこの記録を参照する。
- **ログイン状態**: ログイン成功から 30 日間、ログアウト、または運用側による失効まで有効な「管理者としてログイン済み」の状態。backend が発行して記録し、管理者の記録に結び付く。ブラウザは識別子だけを持ち、ブラウザを閉じても保たれる。GitHub 側のログイン状態とは独立している。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ログインしていない状態で管理者専用と宣言したページとサーバー側の処理を要求した場合、100% が 404 または拒否になり、ページの内容や機能、ログイン画面の存在が一切露出しない。
- **SC-002**: 管理者は秘匿パスのログイン画面を開いてから 30 秒以内にログインを完了しトップページに到達できる。
- **SC-003**: ログイン後、30 日以内であればブラウザを閉じて開き直しても、追加の操作なしに管理者専用の処理が通る。
- **SC-004**: ログアウト操作の直後に管理者専用のページ・処理を要求した場合、100% が 404 または拒否になる。
- **SC-005**: 秘匿パス以外の URL でログイン画面を要求した場合、および GitHub からの戻り先の URL を正当なログインの流れ以外で要求した場合、100% が 404 になり、存在しないページと区別できない。
- **SC-006**: 読者向けの一覧画面は本機能の前後で表示と操作が変わらず、ログインを求められる場面が 0 件である。
- **SC-007**: 許可されていない GitHub アカウントでの承認は 100% ログインが成立せず、管理者専用の処理が通らない。
- **SC-008**: サービス内にパスワードとその照合処理が存在しない。本人確認の失敗回数の管理や回復手順をサービス側で持たない。
- **SC-009**: 管理者が GitHub 上でユーザー名を変更しても、成立済みのログイン状態と管理者を指すサービス内の記録は影響を受けない。
- **SC-010**: backend の管理者専用の処理に、ログイン状態の識別子なし・無効な識別子・失効済みの識別子で要求した場合、frontend を経由したかどうかに関係なく 100% が拒否される。

## Assumptions

- 管理者は本人 1 名で、複数人での運用や権限の使い分けは想定しない。必要になったら本仕様を改訂する。
- 本人確認は GitHub に委ねる。GitHub 側の 2 要素認証や不正ログイン対策はそのまま有効で、サービス側では連続失敗の制限や回復手順を持たない。
- GitHub との連携情報、許可ユーザー名、秘匿パスは運用側が環境の設定として与える。設定手順と変更手順は計画段階で決め、運用ドキュメントに書く。画面からの変更は範囲外。
- ログインの入口の判定は運用側が設定するユーザー名で行う (人が読めて設定しやすいため)。GitHub はユーザー名の変更を許し、旧名は他人が取得できるため、管理者が改名する場合は許可ユーザー名も更新する運用とする。ログイン成立後の本人識別とサービス内の記録は固定 ID で行うため、改名の影響は入口の設定にとどまる。
- 管理者の記録は backend に持つが、権限の種類 (ロール) は持たない。ログインが成立する = 管理者、である。ロールが 2 種類以上になった時点で本仕様を改訂して足す。将来 Digest に登録者などの記録を持たせる場合、その識別子は管理者の記録の固定 ID とする。
- backend への到達制限 (adr/backend/0006 の共有シークレット) は、ログイン状態の照合とは別に維持する。共有シークレットは「frontend からの要求である」ことを、ログイン状態は「管理者の要求である」ことをそれぞれ示す。
- 秘匿パスは推測されにくい十分な長さのランダムな文字列とし、管理者がブックマークして使う。秘匿パスは認証の代わりではなく、管理画面の存在を隠すための追加の層である。認証は GitHub とユーザー名の照合で成立する。
- 404 の表示は既存の「存在しないページ」と同じものを使い、本機能で新しい 404 画面は作らない。
- GitHub のアカウントを失った場合の回復は範囲外。運用側が許可ユーザー名の設定を変更して対応する。
- GitHub が利用できない間はログインできない。本人確認を GitHub に委ねる方針上、受け入れる。
- ログイン状態の有効期間は 30 日固定とし、操作のたびに延長はしない。期間の調整が必要になったら仕様を改訂する。
- ログイン状態は backend の記録として持ち、ブラウザは推測不能な識別子だけを保持する。識別子は backend の記録と照合して初めて意味を持つため、ブラウザから持ち出された識別子は運用側が記録を削除すれば個別に失効できる (FR-019)。全体の失効は記録をすべて削除して行う。
- 有効期限を過ぎたログイン状態の記録は backend が随時削除する。削除のタイミングは実装に委ね、期限切れの記録が残っていても照合では無効として扱う。
- 本機能が作るのは「管理者専用」と宣言する仕組み (ページのガードとサーバー処理の照合) であり、具体的な管理者専用ページは作らない。ログイン状態の照合そのものが管理者専用の処理として存在するため、仕組みは本機能だけで検証できる。既存の `/health` は動作確認用のため保護しない。後続の管理者向け画面 (記事登録画面 001 など) は本機能の仕組みをそのまま使う。
- 読者向けの一覧画面 (002) は本機能で変更しない。ログイン画面への導線は一覧画面に置かず、管理者は秘匿パスのページを直接開く。ログイン後にトップページへ遷移しても、トップページにログイン状態の表示は出さない。
- 監査ログ、ログイン通知、GitHub 以外のプロバイダの追加は範囲外。
- UI は既存のデザインルール (`.agents/rules/frontend-ui-design.md`) とデザイン基礎資料 (Figma) に従う。
