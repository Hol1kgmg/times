# Feature Specification: 記事登録 (Digest 作成) 画面

**Feature Branch**: `001-digest-builder`

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: times の 1 件分の Digest を管理画面上で組み立てる機能

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 記事を集める (Priority: P1)

管理者は気になった記事の URL を 1 件ずつ貼り付けて実行する。システムはその URL から記事タイトルと概要を自動で取得し、どのカテゴリにも属さない「記事候補」として一覧に追加する。管理者はタイトルを手入力せず、入力欄以外を操作せずに、次々と URL を貼り付けて候補を溜めていける。分類や順序はこの時点では考えない。

**Why this priority**: 手作業のデータ作成で最も手間がかかるのがタイトルの転記である。URL からの自動取得だけでも作業量が大きく減り、単体で価値がある。後続の Story はこの候補一覧がなければ成立しない。

**Independent Test**: URL を 3 件連続で貼り付け、一覧に 3 件の候補がタイトル付き・未分類で並ぶことを確認できれば、この Story 単体で価値を提供できる。

**Acceptance Scenarios**:

1. **Given** 候補一覧が空の状態, **When** 記事の URL を貼り付けて実行する, **Then** その記事のタイトルが入った候補が 1 件、どのカテゴリにも属さない状態で一覧に追加される
2. **Given** URL を 1 件投入し終えた直後, **When** 次の URL を貼り付けようとする, **Then** 入力欄は空で、追加の操作なしにそのまま貼り付けられる
3. **Given** 実行してタイトルの取得を待っている状態, **When** 画面を見る, **Then** 処理中であることが分かり、続けて実行することができない
4. **Given** URL として成立しない文字列 (空文字、`http` / `https` 以外), **When** 実行する, **Then** 候補は追加されず、有効な URL の入力を促すエラーがその場に表示される
5. **Given** 同じ記事の URL を既に投入済みの状態, **When** もう一度同じ URL を投入する, **Then** 重複である旨が警告され、候補は二重に追加されない
6. **Given** タイトルを取得できない記事の URL (到達不能、タイトルのないページ、HTML 以外), **When** 実行する, **Then** 候補自体は追加されたうえで、タイトルが取れなかったこと・手で入力する必要があることが示される

---

### User Story 2 - 記事を分類する (Priority: P2)

管理者は溜まった候補を、固定のカテゴリ一覧のいずれかに振り分ける。候補をカテゴリへ移す・別のカテゴリへ移す・未分類へ戻す・カテゴリ内で並び替える・不要な候補を削除する、のいずれも 1 回の操作で完了する。分類の進み具合 (未分類の残数、各カテゴリの件数) は画面を見るだけで分かる。タイトルだけで判断できない候補は、記事を開かずに概要を確認できる。

**Why this priority**: 「集める」と「整える」を分けることが UI 設計の出発点であり、Digest の構成を決めるのはこの段階である。候補がなければ整えるものがないため P1 の後に置く。

**Independent Test**: 候補が数件ある状態で、カテゴリへの移動・未分類へ戻す・並び替え・削除をそれぞれ行い、一覧と件数表示に即時反映されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 分類していない候補がある状態, **When** その候補をあるカテゴリへ移す, **Then** 以降その候補はそのカテゴリのものとして表示される
2. **Given** あるカテゴリに属している候補, **When** 別のカテゴリへ移す, **Then** 一度戻す操作を挟まずに、1 回の操作で移動が完了する
3. **Given** あるカテゴリに属している候補, **When** 未分類の状態へ戻す, **Then** その候補はどのカテゴリにも属さない状態に戻る
4. **Given** 同じカテゴリに複数の候補がある状態, **When** その中で順序を入れ替える, **Then** 表示順だけが変わり、カテゴリは変わらない
5. **Given** 分類作業中, **When** 画面を見る, **Then** 未分類がいくつ残っているかと、各カテゴリに何件あるかが同時に分かる
6. **Given** タイトルだけでは内容が判断できない候補, **When** その候補に注目する, **Then** 記事を開かずに概要 (取得できていれば) を確認できる
7. **Given** 1 件も属していないカテゴリがある状態, **When** 画面を見る, **Then** そのカテゴリは空であることが分かる状態で表示されている
8. **Given** 任意の候補, **When** 削除する, **Then** 候補は一覧から消え、他の候補の順序と分類は保たれる

---

### User Story 3 - 記事の中身を訂正する (Priority: P2)

自動で入ったタイトルが実際と違っていたり、URL を貼り間違えたりしたとき、管理者はその候補を一覧から離れずに直す。訂正は途中でやめられ、その場合は元の内容が保たれる。何度も手を入れておかしくなった候補は、1 回の操作で取得直後の状態 (タイトル・URL) に戻せる。分類と位置は戻す対象に含まれない。

**Why this priority**: 自動取得の失敗を補う手段であり、Story 1 のタイトル取得失敗時に候補を登録できる状態にするために必要。ただし多くの候補は訂正不要なので、Story 1 と同時である必要はない。

**Independent Test**: タイトルの違う候補を訂正して確定し、別の候補で訂正を中断し、さらに別の候補を取得直後の状態へ戻して、それぞれ期待どおりの値になることを確認できる。

**Acceptance Scenarios**:

1. **Given** タイトルが実際と違う候補, **When** その候補を訂正して確定する, **Then** 訂正後の内容が一覧に反映される
2. **Given** 訂正の途中, **When** 確定せずにやめる, **Then** 候補は訂正前のまま変化しない
3. **Given** タイトルを取得できなかった候補, **When** タイトルを手で入力して確定する, **Then** その候補は登録できる状態になる
4. **Given** URL を訂正した候補, **When** 一覧を見る, **Then** その候補は同じ 1 件として扱われ続け、分類やカテゴリ内の位置も保たれる
5. **Given** 何度も手を入れた結果おかしくなった候補, **When** 取得した直後の状態へ戻す, **Then** タイトル・URL がまとめて取得直後の値に戻る
6. **Given** 取得した直後の状態へ戻した候補, **When** その候補の分類を見る, **Then** 分類は変わっていない

---

### User Story 4 - Digest として登録する (Priority: P2)

管理者は整え終わった候補一式を、Digest 1 件分として日付をつけてまとめて登録する。日付は画面を開いた時点で当日が入っており、必要なら変えられる。未分類の候補が残っていれば登録できない。登録できると件数が表示され、一覧は空になって次の Digest 作成を始められる。日付は引き継がれる。今回は送信先 (BFF) はスタブ応答を返すのみで、永続化は行わない。

**Why this priority**: 登録できて初めて「手作業の `sample.json` を置き換える」目的が達成される。Story 2 と同じ優先度だが、Story 1 の候補だけでも登録の流れは検証できるため独立して実装できる。

**Independent Test**: 全候補を分類した状態で登録を実行し、成功表示・件数・一覧が空になること、送信された内容が登録前の一覧と一致することを確認できる。

**Acceptance Scenarios**:

1. **Given** 画面を開いた直後, **When** 日付を見る, **Then** 当日が入っており、そのまま登録できる
2. **Given** 過去の日付で Digest を作りたい, **When** 日付を変える, **Then** 候補一覧には影響せず、登録時に全件へその日付が適用される
3. **Given** 未分類の候補が残っている状態, **When** 登録しようとする, **Then** 登録できず、分類が済んでいないことが分かる
4. **Given** タイトルが空の候補がある状態, **When** 登録しようとする, **Then** 登録できず、どの候補のタイトルが空かが分かる
5. **Given** 候補が 1 件もない状態, **When** 画面を見る, **Then** 登録は実行できない
6. **Given** すべての候補の分類が済んだ状態, **When** 登録を実行する, **Then** 全候補が同じ日付の Digest 1 件分として、画面上のカテゴリ順・カテゴリ内順で送られる
7. **Given** 登録が済んだ, **When** 結果を見る, **Then** 何件登録できたかが分かり、一覧は空になって次の作成を始められる
8. **Given** 登録に失敗した, **When** 結果を見る, **Then** 候補は 1 件も失われておらず、そのまま登録し直せる
9. **Given** 登録が済んだ直後, **When** 次の Digest を作り始める, **Then** 日付の指定はやり直さなくてよい

---

### Edge Cases

- 同じ URL を末尾スラッシュや `#fragment` 違いで入力した場合、別の候補として扱う (正規化は行わない。重複判定は完全一致)。
- タイトル取得に時間がかかる場合 (目安 5 秒超) は取得を打ち切り、タイトル空の候補として追加する (Story 1 Scenario 6 と同じ扱い)。
- 取得先が HTML 以外 (PDF、画像) を返した場合、タイトル・概要とも空で追加する。
- 概要 (ページの説明文) が取得できない場合、候補に概要は表示されない。タイトルの取得可否には影響しない。
- URL を訂正しても、タイトルと概要の再取得は行わない (タイトルは手で直す)。
- ページを再読み込みまたは離脱した場合、候補一覧は失われる。候補が残っていれば、ブラウザ標準の離脱確認を出す。
- 候補が 100 件を超えても操作できること。それ以上の件数は想定しない。
- 登録成功後は候補一覧が空になるため、離脱確認は出ない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 管理者は記事 URL を 1 件ずつ入力して候補一覧に追加できなければならない (MUST)。追加後、入力欄は空に戻る。
- **FR-002**: システムは追加された URL から記事タイトルと概要 (ページの説明文) を自動取得し、候補に設定しなければならない (MUST)。タイトルを取得できない場合は候補をタイトル空で保持し、手入力が必要であることを示す。概要は取得できた場合のみ持つ。
- **FR-003**: タイトル取得中は、次の URL の実行を受け付けてはならない (MUST NOT)。処理中であることを表示する。
- **FR-004**: システムは `http` / `https` 以外の URL と空入力を拒否し、理由をその場に表示しなければならない (MUST)。
- **FR-005**: システムは完全一致で重複する URL の候補追加を拒否し、重複である旨を警告しなければならない (MUST)。
- **FR-006**: 各候補は、URL・タイトル・概要 (任意)・取得直後のタイトルと URL・カテゴリ (未分類可)・カテゴリ内の並び順・タイトル取得状態 (取得中 / 取得済み / 失敗) を持たなければならない (MUST)。
- **FR-007**: カテゴリは固定の一覧「セキュリティ、ホットトピック、IT系、UI系、AI系、面白そうなツール・サービス、その他」とし、この順序で表示する (MUST)。管理者によるカテゴリの追加・変更・並び替えは行わない。
- **FR-008**: 管理者は候補を、未分類からカテゴリへ、カテゴリから別のカテゴリへ、カテゴリから未分類へ、それぞれ 1 回の操作で移動できなければならない (MUST)。
- **FR-009**: 管理者は同一カテゴリ内で候補の並び順を変更できなければならない (MUST)。
- **FR-010**: システムは候補一覧をカテゴリごとにまとめて表示し、空のカテゴリも表示し、未分類の残数と各カテゴリの件数を常時表示しなければならない (MUST)。
- **FR-011**: 管理者は候補を削除でき、削除後も他の候補の分類と順序は保たれなければならない (MUST)。
- **FR-012**: 管理者は候補のタイトルと URL を訂正でき、確定前にやめた場合は訂正前の値が保たれなければならない (MUST)。URL を訂正しても候補は同じ 1 件として扱われ、分類と位置は保たれる。
- **FR-013**: 管理者は候補を 1 回の操作で取得直後の状態 (タイトル・URL) に戻せなければならない (MUST)。分類と位置は戻す対象に含めない。
- **FR-014**: Digest は全体で 1 つの日付を持ち、初期値は画面を開いた日とし、管理者が変更できなければならない (MUST)。登録成功後も日付は保持する。
- **FR-015**: 管理者は候補一式を Digest 1 件分として登録でき、送信データはカテゴリ / タイトル / URL / 日付を候補ごとに持つ配列で、カテゴリの固定順とカテゴリ内の並び順を保たなければならない (MUST)。日付は全候補で同一とする。
- **FR-016**: システムは候補が 0 件、未分類の候補がある、タイトル空の候補がある、のいずれかのとき登録を拒否し、理由と該当候補を示さなければならない (MUST)。
- **FR-017**: 登録に成功したとき、システムは登録件数を表示し、候補一覧を空にしなければならない (MUST)。
- **FR-018**: 送信先 (BFF) は今回はスタブ応答を返すのみとし、受け取ったデータの永続化を行ってはならない (MUST NOT)。登録失敗時、候補一覧は失われてはならない (MUST NOT)。
- **FR-019**: 候補一覧はページ滞在中のみ保持し、離脱・再読み込みで失われてよい。候補が残っている状態での離脱には確認を出す (MUST)。
- **FR-020**: 画面の保護 (認証) は本機能の範囲外とする。認証は別機能として用意し、本機能は認証なしで動作する。
- **FR-021**: 外国語タイトルの言語判定・翻訳・翻訳漏れの警告は本機能の範囲外とし、後続の機能で実装する。外国語タイトルは FR-012 の訂正で手動で書き換えられる。

### Key Entities

- **記事候補 (Candidate)**: Digest に入れる予定の記事 1 件。URL、タイトル、概要 (任意)、取得直後のタイトルと URL (戻す用)、カテゴリ (未分類可)、カテゴリ内の並び順、タイトル取得状態を持つ。
- **カテゴリ (Category)**: 固定の 7 つ。順序も固定。候補はいずれか 1 つに属するか、未分類。
- **Digest (送信データ)**: 候補一覧を送信用に組み立てたもの。1 つの日付と、カテゴリ / タイトル / URL / 日付を候補ごとに持つ配列。既存の手書きデータ (`sample.json` 相当) と同じ形。1 回の登録で 1 件。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 記事 10 件の Digest が、URL を貼り始めてから登録完了まで 5 分以内に終わる。
- **SC-002**: 記事 1 件の追加に必要な操作が「URL を貼る」「実行する」の 2 つに収まり、10 件連続で投入する間に入力欄以外を操作する必要がない。
- **SC-003**: 到達可能な一般的な記事ページの 90% 以上で、タイトルが自動取得される。
- **SC-004**: 候補 10 件の分類が、記事を開き直すことなく、1 件あたり 1 回の操作で完了する。
- **SC-005**: 登録されたデータの内容と順序が、登録直前の候補一覧と 100% 一致し、未分類の候補が混ざったまま登録されることが起こらない。
- **SC-006**: 不正な URL、重複 URL、登録条件未達のいずれでも、管理者は次に何をすべきかを画面上の表示だけで判断できる。

## Assumptions

- 利用者は管理者本人 1 名であり、同時に複数人が同じ Digest を編集することは想定しない。
- タイトルと概要の自動取得は、対象ページが公開されており認証なしで到達できることを前提とする。概要はページの説明文 (メタ情報) 程度とし、本文の要約は行わない。
- カテゴリの固定一覧は本機能の一部として定義する。変更が必要になったら仕様を改訂する。
- 分類と並び替えはポインタ操作を前提にせず、選択と上下移動で完了する。ドラッグ操作は必須としない。
- 翻訳機能は後続の機能で追加する。FR-013 の「取得直後の状態」が翻訳前のタイトルの代わりになる。
- 送信先の BFF は frontend のサーバー側境界を指し、backend の永続化は本機能の範囲外。登録成功はスタブ応答で判定する。
- 候補一覧の一時保存 (下書き)、過去の Digest の閲覧・再編集は範囲外。
- 認証は別機能で用意する。本機能の完了時点では画面は保護されておらず、公開環境に出す前に認証機能を先に導入する。
- 既存の一覧・詳細画面 (items) とは独立した画面として追加し、既存画面の変更は行わない。
- UI は既存のデザインルール (`.agents/rules/frontend-ui-design.md`) に従う。
